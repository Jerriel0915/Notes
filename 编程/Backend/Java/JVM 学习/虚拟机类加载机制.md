### 1. 概述

Java 虚拟机把描述类的数据从 Class 文件加载到内存，并对数据进行校验、转换解析和初始化，最终形成可以被虚拟机直接使用的 Java 类型，这个过程被称作虚拟机的**类加载机制**。诸如 C 系语言是在编译期间进行连接，对 Java 而言，类的加载、连接和初始化是在程序运行期间完成的，这提供了很高的扩展性和灵活度。

一个类的生命周期经历**加载 （Loading）**、**验证（Verification）**、**准备（Preparation）**、**解析（Resolution）**、**初始化 （Initialization）**、**使用（Using）**和**卸载（Unloading）**七个阶段。其中验证、准备、解析可以统称为**连接（Linking）**。

### 2. 加载
#### 2.1 类加载器

JVM 启动时并不会一次性加载所有的类，大部分类都是在用之前才进行加载。在加载阶段需要完成三件事：

1. 获取类的二进制字节流（不只是硬盘，也可以是计算生成（动态代理）或者是网络 I/O 等）
2. 将字节流代表的静态存储结构转换为方法区的运行时数据结构
3. 在内存中所生成一个 Class 对象作为访问入口

每个非数组类或接口都有一个引用指向对应的**类加载器** `ClassLoader`。加载阶段既可以使用内置的引导类加载器来完成，也可以由自定义的类加载器去完成（重写一个类加载器的 `findClass()` 或 `loadClass()` 方法，不过通常只重写 `findClass()` 方法即可，`loadClass()` 涉及到双亲委派模型，可见下文）

```Java
class Class<T> {
  ...
  private final ClassLoader classLoader;
  @CallerSensitive
  public ClassLoader getClassLoader() {
     //...
  }
  ...
}
```

数组类本身不通过 `Classloader` 加载（因为没有对应的二进制字节流），采用 JVM 直接在内存中生成。但数组类与类加载器仍然有很密切的关系，因为数组类的元素类型（Element Type，指的是数组去掉所有维度的类型）最终还是要靠类加载器来完成加载。

#### 2.2 类加载器种类

按照层级从上至下，分别有：

- **Bootstrap ClassLoader（启动类加载器）**  
	用 C++ 实现，是 JVM 的一部分。负责加载 `<JAVA_HOME>/lib` 下的核心类库，比如 `rt.jar`、`resources.jar` 等。它就是**顶级加载器**了，没有父加载器，在 Java API 中通常表示为 `null`。
- **Extension ClassLoader（扩展类加载器）**  
    由 `sun.misc.Launcher$ExtClassLoader` 实现，负责加载 `<JAVA_HOME>/lib/ext` 目录下的扩展类库，或者由 `java.ext.dirs` 系统变量指定的目录。它的父加载器是 Bootstrap ClassLoader。
- **Application ClassLoader（应用程序类加载器）**  
    由 `sun.misc.Launcher$AppClassLoader` 实现，负责加载用户类路径（`classpath`）上的类库，也就是我们自己写的代码和第三方 jar 包。它的父加载器是 Extension ClassLoader。
- **自定义类加载器**  
    通过继承 `java.lang.ClassLoader` 实现自己的加载器，通常用于从网络、加密文件等特殊来源加载类。如果不特别指定，它的父加载器默认是 Application ClassLoader。


> [!NOTE] 扩展
>  - **`rt.jar`**：rt 代表“RunTime”，`rt.jar` 是 Java 基础类库，包含 Java doc 里面看到的所有的类的类文件。
> - Java 9 引入模块系统后不再使用 `rt.jar` 和扩展目录机制，扩展类加载器由平台类加载器（Platform Class Loader）取代。启动、平台和应用类加载器分别定义不同的运行时模块；不能简单概括为除 `java.base` 外的所有模块都由平台类加载器加载。

一个小例子可以演示这个层级关系：
```Java
public class PrintClassLoaderTree {

    public static void main(String[] args) {

        ClassLoader classLoader = PrintClassLoaderTree.class.getClassLoader();

        StringBuilder split = new StringBuilder("|--");
        boolean needContinue = true;
        while (needContinue){
            System.out.println(split.toString() + classLoader);
            if(classLoader == null){
                needContinue = false;
            }else{
                classLoader = classLoader.getParent();
                split.insert(0, "\t");
            }
        }
    }

}
```

结果（JDK 8，如果是 9+版本 `ExtClassLoader` 会被 `PlatformClassLoader` 所替代）：
```plain
|--sun.misc.Launcher$AppClassLoader@18b4aac2
    |--sun.misc.Launcher$ExtClassLoader@53bd815b
        |--null
```

#### 2.3 双亲委派模型
> The ClassLoader class uses a **delegation model** to search for classes and resources. Each instance of ClassLoader has an associated parent class loader. **When requested to find a class or resource, a ClassLoader instance will delegate the search for the class or resource to its parent class loader before attempting to find the class or resource itself.** The virtual machine's built-in class loader, called the "bootstrap class loader", does not itself have a parent but may serve as the parent of a ClassLoader instance.

总的来说，**当一个类加载器收到类加载请求时，它首先不会自己尝试加载这个类，而是把这个请求委派给父加载器去完成；只有当父加载器反馈自己无法完成加载时，子加载器才会尝试自己去加载。**

> 双亲委派这个词听着高级，但其实也就那么回事。但是我很想问问当时的翻译者，*delegation model*（委派模型）这个词经过翻译是怎么多出来的“双亲”？双亲体现在哪了？因此下文不再提及“双亲”。

委派思想主要体现在 `java.lang.ClassLoader` 的 `loadClass()` 中：

```Java
protected Class<?> loadClass(String name, boolean resolve)
        throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 第一步：检查该类是否已经被当前加载器加载过
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            long t0 = System.nanoTime();
            try {
                if (parent != null) {
                    // 第二步：如果父加载器存在，委托给父加载器加载
                    c = parent.loadClass(name, false);
                } else {
                    // 如果父加载器不存在（即当前是Bootstrap），委托给启动类加载器
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器抛异常，说明它无法加载，忽略此异常继续
            }

            if (c == null) {
                // 第三步：父加载器未能加载，调用自身的findClass尝试加载
                long t1 = System.nanoTime();
                c = findClass(name);

                // 记录加载耗时等统计信息
                sun.misc.PerfCounter.getParentDelegationTime().addTime(t1 - t0);
                sun.misc.PerfCounter.getFindClassTime().addElapsedTimeFrom(t1);
                sun.misc.PerfCounter.getFindClasses().increment();
            }
        }
        if (resolve) {
            // 第四步：如果resolve为true，连接该类（分配内存、解析符号引用等）
            resolveClass(c);
        }
        return c;
    }
}
```

> JVM 判断两个 Java 类是否相同，不仅仅看类全名是否相同，还会比较类加载器是否相同。

至于为什么要采用委派机制，核心需求就是保护平台 API，防止核心类库被恶意注入或伪造。委派模型的本质是**对类加载器职权范围的一种排序约定**：越靠近根的加载器越权威，加载的类越基础；越靠近叶子的加载器处理的范围越具体。它通过 “先委托后自加载” 保证了核心类库的唯一性和安全性，但同时也牺牲了一定的灵活性。

### 3.  验证
验证是连接阶段的第一步，这一阶段的目的是确保 Class 文件的字节流中包含的信息符合《Java 虚拟机规范》的全部约束要求，保证这些信息被当作代码运行后不会危害虚拟机自身的安全。
